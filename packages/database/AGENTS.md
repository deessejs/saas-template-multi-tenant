# `packages/database` — agent invariants

## Generated auth schema — absolute rule

The file `src/schema/auth.ts` is **generated by the better-auth CLI**. You must **never** edit it by hand.

**Generation command** (from the repo root): `pnpm auth:generate`.
See also `pnpm auth:generate --help` at the workspace level.

### Why

The better-auth CLI rewrites the file **in full** on every run. Any manual change will be silently overwritten. Editing it wastes work; pushing without re-generating breaks alignment with `@workspace/auth`.

In addition, the **Drizzle relations** declared in that file (`userRelations`, `sessionRelations`, `accountRelations`) must stay aligned with the schema: the CLI emits them with the correct `relationName` for `experimental.joins: true`. Hand-editing them breaks that alignment.

### Affected tables

The four tables in `src/schema/auth.ts` — `user`, `session`, `account`, `verification` — are owned by better-auth. Do not add columns, indexes, or constraints to them.

### Extending auth data

**Do not** add inline columns to `auth.ts`. Instead, create a **1-to-1 satellite table** in `src/schema/<feature>.ts` (e.g. `profile`, `settings`, `preferences`):

```ts
// src/schema/profile.ts
export const profile = pgTable("profile", {
  userId: text("user_id").primaryKey().references(() => user.id, { onDelete: "cascade" }),
  // … your custom fields here
})

export const profileRelations = relations(profile, ({ one }) => ({
  user: one(user, { fields: [profile.userId], references: [user.id] }),
}))
```

A satellite table survives regenerations, isolates the domain, and avoids merge conflicts.

### Adding a new custom table

1. Create `src/schema/<feature>.ts` with the table + its `relations()`.
2. Re-export from `src/schema/index.ts`.
3. If a `src/schema/relations.ts` aggregator convention is in use, add it there too.
4. Run `pnpm db:generate` to produce the migration.
5. `pnpm db:push` in dev, `pnpm db:migrate` in staging/prod.

### When in doubt

Read `docs/guides/better-auth/setup.md` § "Drizzle Adapter" and `docs/guides/better-auth/pitfalls.md` first. Both specifically cover Drizzle integration and known pitfalls (`usePlural`, `relationName`, CLI overwrite).

## Connection pool (`src/client.ts`)

Do not modify `src/client.ts` without a documented reason.

Pool defaults are tuned for **Neon / PgBouncer / Vercel Fluid Compute**:

| Option | Value | Why |
|---|---|---|
| `prepare` | `false` | Required behind transaction-mode poolers (extended-query protocol is incompatible). |
| `max` | `10` | Per Lambda/worker. Revisit if a higher Vercel `maxExecutionDuration` is opted in. |
| `idle_timeout` | `60` | Neon compute suspends after 5 min; 20 s previously caused ECONNRESET. |
| `max_lifetime` | `1800` | Recycle connections every 30 min. |

Key invariants in the file:

- **`buildStub()` is the CLI-passthrough Proxy.** It throws on any non-inspector property access when `DATABASE_URL` is unset (covers all known + future Drizzle methods, plus `db.query.users.*` chain). Don't reduce this to a quieter error or return `undefined` — fail loudly so misuse surfaces at first access, not at first SQL execution.
- **`closeDb()` is exported.** Drains the pool with `timeout: 0.3` (fits Vercel's 500 ms graceful shutdown budget). On Vercel, **the right tool for idle-connection hygiene is `attachDatabasePool(pool)` from `@vercel/functions`** wired at the route entrypoint — SIGTERM alone is not enough.
- **HMR guard via `globalThis.__workspace_db`** is gated on `NODE_ENV !== "production"`. Production uses module-local cache only.

See `docs/internal/learnings/drizzle/client-init.md` for the full design rationale.

## Tests — PGlite-backed (`@workspace/database/test-utils`)

The package exposes a **sub-path export** for test utilities. **Never** reach into pg-mem or build your own `postgres(...)` pool.

```ts
import { setupTestDb, cleanup, type Drizzle } from "@workspace/database/test-utils"
import { afterAll, beforeAll } from "vitest"

let db: Drizzle

beforeAll(async () => {
  db = await setupTestDb()
})

afterAll(async () => {
  await cleanup()
})
```

What this gives you:

- **Real Postgres in WASM** (`@electric-sql/pglite`) — not emulation. No Docker, no env var, no schema drift.
- **Schema pushed via `pushSchema` from `drizzle-kit/api`** — reads the same `schema/index.ts` the production runtime uses. No duplicated SQL.
- **Typed Drizzle client** (`PgliteDatabase<typeof schema>`) — not a partial duck-type.
- **Idempotent lifecycle** — `setupTestDb` is lazy, `cleanup` can be called multiple times.

Critical limitations:

- **PGlite has a single WASM connection.** Running transactions in parallel (`Promise.all([tx1, tx2])`) **deadlocks**. Serialize.
- **One `setupTestDb` per process.** Sharing across Vitest workers requires one module instance per worker (Vitest's default with `pool: 'threads'`).
- The `pushSchema` import is `drizzle-kit/api` for `drizzle-kit ^0.31`. At the bump to **1.0**, rename to `drizzle-kit/api-postgres` (the comment in `src/test-utils.ts` calls this out).

Never:

- Reintroduce `pg-mem` — its emulated SQL was a drift liability.
- Build your own `postgres(...)` pool in tests. Consume `setupTestDb`.
- Duplicate the schema SQL anywhere. `pushSchema` reads the source.

## Build output — `.js` extensions required

`tsc` is invoked with `--rewriteRelativeImportExtensions` (see `package.json:scripts.build`). All **relative imports in source MUST include the `.js` suffix** (e.g., `export * from "./auth.js"`).

The rewrite only kicks in for imports that already have `.js` in source. Skipping the `.js` suffix breaks `dist/` portability for non-Vitest consumers (plain Node ESM requires explicit extensions and won't resolve `export * from "./auth"` without it).

## Code style — arrow functions for TS exports

For new exported functions in TS files, use the **arrow style**:

```ts
// ✅ preferred
export const setupTestDb = async (): Promise<Drizzle> => { ... }
export const cleanup = async (): Promise<void> => { ... }

// ❌ avoid (legacy convention)
export async function setupTestDb(): Promise<Drizzle> { ... }
export async function cleanup(): Promise<void> { ... }
```

The arrow style keeps the declaration shape consistent with non-exported helpers and matches the global preference captured in `feedback-ts-arrow-style` memory. Apply this rule to **new code**; refactoring existing exports is optional but encouraged when touching the file.
