# Drizzle migrations — deep dive

> Snapshot: **2026-07-16**. Complements `README.md` (schema organization), `drizzle-kit.md` (commands reference), and `client-init.md` (singleton + Proxy). This file focuses on the **migration workflow** itself — file format, generation mechanics, runtime application, and the long-term 1.0 roadmap.
>
> Companion to `packages/database/AGENTS.md` invariant "do not edit `src/schema/auth.ts` by hand".

---

## 1. TL;DR

Drizzle migrations are **declarative SQL snapshots generated from your Drizzle schema** and tracked through a per-folder journal. As of mid-2026, the workflow is mature on the 0.31 line and being **rewritten under the hood** for the 1.0 release (the "alternation-engine" branch). Two facts drive most of this doc:

- **`drizzle-kit generate` is the only safe source of new migrations**. Manual SQL is allowed via `--custom` but discouraged.
- **There's a known silent-overwrite bug** ([drizzle-team/drizzle-orm#5774](https://github.com/drizzle-team/drizzle-orm/issues/5774)) that strikes when the journal gets out of sync with on-disk SQL files. **Run `drizzle-kit check` in CI** to catch this.

For our repo (`@workspace/database`), the auth tables in `src/schema/auth.ts` are CLI-generated by better-auth — the migration workflow must coexist with that regeneration cycle (see §9).

## 2. End-to-end migration lifecycle

### 2.1 Authoring — `drizzle-kit generate`

```bash
pnpm db:generate --name=add-user-profile
```

What it does, mechanically:

1. Reads `src/schema/index.ts` (per `drizzle.config.ts`).
2. Composes a JSON snapshot of the **current** schema state.
3. Reads the most recent snapshot in `drizzle/meta/*.json`.
4. Diffs the two snapshots.
5. Emits a new `drizzle/<timestamp>_<slug>/migration.sql` + matching snapshot.
6. If a column or table is missing from the previous snapshot but present now, prompts for an explicit `rename` (otherwise Drizzle can't infer "was this a rename or a drop+create?").

The output SQL is committed alongside the schema change. **One PR = one schema diff = one migration folder.**

### 2.2 Applying — `drizzle-kit migrate`

```bash
pnpm db:migrate
```

- Reads `drizzle/meta/_journal.json` to find what's already applied.
- Connects to `DATABASE_URL`, creates a `__drizzle_migrations` table if missing.
- Applies missing migrations in order.
- Records each as applied.

Alternatively, **runtime migration via `migrate()`** (`drizzle-orm/<driver>/migrator`):

```ts
import { migrate } from "drizzle-orm/postgres-js/migrator"
import { db } from "./client.js"

await migrate(db, { migrationsFolder: "./drizzle" })
```

Used in serverless environments where CLI access is awkward. Trade-off: requires runtime DB access at startup.

### 2.3 Skipping migrations — `drizzle-kit push` (dev only)

```bash
pnpm db:push
```

Pushes the current schema directly without writing a migration file. **Never** use in staging or prod:

- No audit trail.
- No rollback path.
- May silently drop data on column-type changes (e.g., `text` → `int`).
- Will diverge from `main`'s committed migration history within minutes.

Acceptable in early dev iteration. Should be **disabled in CI for protected branches**.

### 2.4 Reverse — `drizzle-kit pull` / `introspect`

```bash
pnpm db:push  # or
pnpm drizzle-kit pull
```

Generates Drizzle schema files from an **existing** Postgres database. Use case: onboarding an existing project into Drizzle, or recovering after a hand-applied schema change. Output is a starting point — usually needs manual cleanup (relations, comments, naming).

## 3. File format internals

### 3.1 Migration folder structure (current 0.31 format)

```
drizzle/
├── meta/
│   ├── _journal.json          ← ordered list of applied migrations
│   └── 0000_snapshot.json     ← schema state after migration N
├── 0000_boring_steel_serpent.sql
├── 0001_xxx.sql
└── 0002_yyy.sql
```

Older flat layout had `drizzle/0000_xxx.sql` directly. Newer (1.0) layout will be `drizzle/<timestamp>_<slug>/migration.sql` (folder per migration).

Our repo uses the **flat legacy format** — `drizzle/0000_boring_steel_serpent.sql` only, with `meta/_journal.json` and `meta/0000_snapshot.json`.

### 3.2 `_journal.json` schema (v7)

```json
{
  "version": "7",
  "dialect": "postgresql",
  "entries": [
    {
      "idx": 0,
      "version": "7",
      "when": 1783351219509,
      "tag": "0000_boring_steel_serpent",
      "breakpoints": true
    }
  ]
}
```

- `version: "7"` — snapshot schema version, **not** the drizzle-kit version.
- `when` — Unix ms timestamp of when the migration was generated.
- `tag` — matches the `.sql` filename (minus extension).
- `breakpoints` — if `true`, drizzle can split the SQL at `--> statement-breakpoint` markers for partial application.

### 3.3 `--> statement-breakpoint`

In a migration file:

```sql
CREATE TABLE "user" (...);
--> statement-breakpoint
CREATE INDEX "user_email_idx" ON "user" ("email");
```

Each statement is independently applicable. Useful when:
- A migration mixes safe DDL (CREATE TABLE) with potentially-long statements (CREATE INDEX on huge tables).
- You want a partial migration to commit if some statements succeed.

`drizzle-kit generate` produces these by default for any DDL beyond trivial `CREATE TABLE`.

### 3.4 Snapshot v7 internals

`meta/0000_snapshot.json` is **the source of truth** for what drizzle-kit considers "applied". It contains:

- All tables with their columns, types, nullability, defaults.
- Indexes (name, columns, method, with-options).
- Foreign keys (name, from/to columns, onDelete/onUpdate actions).
- Unique constraints, check constraints, policies.
- Enums, sequences, schemas, views, roles.
- Schema filter, dialect.

The diff between two snapshots is the migration. **A wrong snapshot = a wrong migration** — which is exactly what [#5774](https://github.com/drizzle-team/drizzle-orm/issues/5774) is about.

## 4. `generate` mechanics and renames

### 4.1 What `generate` detects automatically

| Change | How it's detected |
|---|---|
| Add column | New key in `columns` object |
| Drop column | Missing key |
| Add table | New key in `tables` |
| Drop table | Missing key |
| Change type | Diff in column `type` |
| Add index | New entry in `indexes` |
| Change nullable | Diff in `notNull` |
| Add default | Diff in `default` |

### 4.2 What `generate` cannot infer — renames

If you rename a column, drizzle-kit sees it as **drop + create**. The diff would emit `ALTER TABLE ... DROP COLUMN x; ALTER TABLE ... ADD COLUMN y;` — destructive.

To avoid data loss, drizzle-kit **prompts** at the CLI:

```
? Do you want to rename the column "email" to "email_address"?
> Yes, rename
  No, drop and create
```

Always pick rename when the intent is rename. Otherwise you lose data.

### 4.3 Custom migrations (`--custom`)

```bash
pnpm drizzle-kit generate --custom --name=seed-default-roles
```

Produces an empty `.sql` file for hand-written DDL or DML. Use cases:

- Seed data (`INSERT INTO ...`).
- `CREATE FUNCTION` / stored procedures.
- `CREATE TRIGGER` (no Drizzle-level representation yet).
- Schema changes not yet expressible in Drizzle (e.g., `ALTER TYPE ... RENAME VALUE`).

Convention: prefix the slug with `seed-` or `custom-` so reviewers immediately see "this isn't a Drizzle-generated diff".

### 4.4 Idempotency

`generate` is **idempotent over an unchanged schema**: re-running it produces no new migration folder. If the schema hasn't changed since the last generation, you get:

```
No schema changes found
```

This is the foundation for safe CI gates (see §6).

## 5. Known bugs and gotchas

### 5.1 [#5774](https://github.com/drizzle-team/drizzle-orm/issues/5774) — silent snapshot overwrite

**Status (mid-2026): OPEN, no fix merged.**

The bug: `drizzle-kit generate` derives the next migration index from `_journal.json` alone. If the journal says idx=2 but the `drizzle/` folder contains a `0005_xxx.sql`, generate silently overwrites the on-disk `0005_*.sql` snapshot with a new (different) one.

Reproduction path:
1. Generate `0000`, `0001`, `0002` migrations.
2. Manually edit `_journal.json` (or roll it back) so entries are `0000, 0001`.
3. Run `generate` again — the next file is named `0002_xxx.sql` (correct, from journal), but its **content** may collide with what was on disk as `0002_yyy.sql` previously.

**Mitigation in this repo**: add `pnpm db:check` to CI. It validates that the snapshot sequence is consistent with the on-disk SQL files.

### 5.2 Windows path issues — PR #5518

Drizzle-kit uses path separators that don't normalize on Windows for `embeddedMigrations`. The fix is on the `beta` branch, not yet in 0.31.10. Tracked in [drizzle-team/drizzle-orm#5518](https://github.com/drizzle-team/drizzle-orm/pull/5518).

**Mitigation**: develop on a Unix-like environment (Codespaces, WSL2, or git-bash). Document this constraint for Windows contributors.

### 5.3 `migrations table` config

```ts
// drizzle.config.ts
defineConfig({
  dialect: "postgresql",
  schema: "./src/schema/index.ts",
  out: "./drizzle",
  migrations: {
    table: "__drizzle_migrations",  // default
    schema: "public",              // default
    prefix: "timestamp_",          // 1.0+
  },
})
```

The `prefix` option is new in 1.0+ (`index` / `timestamp` / `unix` / `supabase` / `none`). Defaults vary by version. Our config doesn't set these — defaults apply.

### 5.4 `drizzle-kit check` vs `drizzle-kit up`

- `check` — validates that the **generated** migration journal is consistent with what's on disk. Free, idempotent, safe to run in CI on every PR.
- `up` — upgrade the snapshot format of **previously** generated migrations to the current version. Run once after a drizzle-kit major bump. Destructive if the new format has different semantics.

### 5.5 Partial / batched migration failures

Postgres DDL is transactional — either the entire migration applies or none of it. Drizzle sets `breakpoints: true` by default so each statement can be split, but the framework-level transaction still wraps everything.

If a migration fails mid-way:
- Postgres rolls back the transaction.
- The `__drizzle_migrations` table does NOT record the failed migration.
- Re-running `migrate` retries from the same point.

**Gotcha**: if you hand-edit a migration file after it's been partially applied, you can corrupt the journal. Never hand-edit applied migrations.

## 6. CI integration

### 6.1 GitHub Actions — pre-merge gate

```yaml
# .github/workflows/drizzle.yml
name: drizzle
on: [pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter @workspace/database db:check
      - run: pnpm --filter @workspace/database db:generate --name=ci-canary
      - uses: mskelton/[email protected]
        with:
          pattern: packages/database/drizzle/
          diff: 'auto'
```

If `db:check` fails (journal inconsistency), the PR is blocked. If `db:generate` produces a new file but the PR doesn't include it, the diff check fails.

### 6.2 Pre-commit hook

```bash
#!/bin/sh
# .husky/pre-commit
pnpm --filter @workspace/database db:check
```

Catches the case where a developer changed `src/schema/` but forgot to run `db:generate` and commit the migration.

### 6.3 The "regen-and-diff" pattern (recommended, not yet implemented)

A more robust gate: in CI, regenerate from scratch and `diff` against the committed version. Any divergence means the committed migration drifted from the schema.

```bash
# In CI:
cp -r drizzle /tmp/drizzle-committed
pnpm db:generate --name=ci-regen
diff -r /tmp/drizzle-committed drizzle
```

This is **the strongest check** but requires the `drizzle` folder to be deterministic across machines — which is mostly true in 0.31+.

### 6.4 Our current state (this repo)

`packages/database/package.json` defines `db:check` script but **no CI workflow calls it**. See §10 for the follow-up issue.

## 7. Production patterns

### 7.1 Long-running migrations

Drizzle generates SQL one statement at a time, but **the runtime of a single statement** can be unbounded:

- `CREATE INDEX CONCURRENTLY` on a 100M-row table: minutes to hours.
- `ALTER TABLE ... ALTER COLUMN TYPE`: rewrites the entire table. Takes a table-level ACCESS EXCLUSIVE lock.

For Postgres specifically, prefer:

```sql
-- not just CREATE INDEX, but CONCURRENTLY
CREATE INDEX CONCURRENTLY "user_email_idx" ON "user" ("email");
```

Drizzle generates plain `CREATE INDEX` by default. You'll need to hand-edit the migration (or use `--custom`) to add `CONCURRENTLY`. Trade-off: `CREATE INDEX CONCURRENTLY` cannot run in a transaction (must be `--custom` outside a transaction wrapper).

### 7.2 Locking

Postgres takes ACCESS EXCLUSIVE on most ALTER TABLE operations. For high-traffic tables:

- Run during low-traffic windows.
- Or use `pg_repack` / `pg_squeeze` for online table rewrites.
- Or use logical replication to migrate to a new table.

Drizzle-kit doesn't model lock duration — it's your responsibility.

### 7.3 Down-migrations

Drizzle-kit does **not** generate down-migrations. Two strategies:

- **Reversible by hand**: for each forward migration, write a paired `--custom` migration with the inverse DDL.
- **Snapshot-based restore**: keep `pg_dump` snapshots per deploy; rollback by restoring the snapshot.

The `1.0` rewrite is rumored to support reverse migrations; track the `alternation-engine` branch.

### 7.4 Multi-tenant considerations

For sharded / multi-tenant DBs:

- Generate once, apply per tenant.
- Track per-tenant migration state in your own table, not `__drizzle_migrations`.
- Consider `pg_advisory_lock` around the migrate step to prevent concurrent runs.

Drizzle-kit doesn't ship multi-tenant helpers. The pattern is "run drizzle-kit migrate in a CI job per tenant".

## 9. Better-auth CLI ↔ migrations interplay

### 9.1 The collision surface

`packages/database/src/schema/auth.ts` is **generated by `pnpm auth:generate`** (see `packages/database/AGENTS.md`). When better-auth adds a column or changes a relation name:

1. The CLI rewrites `src/schema/auth.ts`.
2. The next `pnpm db:generate` diffs vs the previous snapshot → emits a migration.
3. The migration is committed alongside the auth bump.

This works **as long as the regeneration is the only change**. The foot-gun:

> If the auth CLI emits new tables (e.g., `organization`, `member`, `invitation` when the `organization()` plugin is enabled — see `docs/guides/better-auth/org.md`), the migration will include CREATE TABLE statements for those tables. That's correct.

The risk surface:

- **In-place column changes in the auth CLI**: drizzle-kit sees it as drop + create unless the auth CLI emits identical Drizzle column definitions. Today the CLI emits identical definitions, so renames are detected correctly. If this changes, **review the migration diff before merging**.
- **Satellite tables in `src/schema/<feature>.ts`** don't interact with the auth CLI at all. Their migrations are clean.

### 9.2 What to check when the auth CLI regenerates

A 3-step checklist for any PR that bumps better-auth:

1. `pnpm auth:generate` — regenerate the schema.
2. `git diff src/schema/auth.ts` — confirm only the intended changes.
3. `pnpm db:generate --name=<issue-or-rfc-tag>` — emit the matching migration. Review the SQL.

If the auth CLI's emitted changes are unexpected (e.g., it silently drops a column), **stop and check `docs/guides/better-auth/pitfalls.md`** before proceeding.

### 9.3 When `auth.ts` is regenerated after a long gap

If a branch has stale auth schema (e.g., 3 months old), regenerating may emit a large diff. The corresponding migration may include:

- New tables (if the CLI started emitting them).
- Dropped tables (if the CLI stopped emitting them).
- Column-type changes (rare but possible).

In this case, **coordinate the schema bump with a manual migration review** — don't auto-merge.

## 12. Closing

The 0.31 migration workflow is mature and the docs above cover what's currently safe to lean on. The 1.0 rewrite will change three things that matter:

1. **Folder structure** (one-folder-per-migration with timestamp prefix).
2. **Subpath renames** (`drizzle-kit/api` → `drizzle-kit/api-postgres`).
3. **Commutative migrations** (parallel-safe diffs).

Until that upgrade lands, the senior path is:

- Run `pnpm db:check` in CI (recommended addition — see §10).
- Hand-edit only when adding `CONCURRENTLY` or other Postgres-specific DDL (use `--custom`).
- Coordinate `auth.ts` regeneration with migration review (§9).
- Trust the journal as the source of truth for "what's applied" — never hand-edit applied SQL.

The single biggest risk in the current 0.31 line is [#5774](https://github.com/drizzle-team/drizzle-orm/issues/5774). Catching it requires running `db:check` in CI on every PR — a 1-line CI step that buys disproportionate safety.
