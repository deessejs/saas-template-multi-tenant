# Drizzle ORM schemas — internal learning notes

> Scope: how we model, migrate, and connect to Postgres in `packages/database`, grounded in the Drizzle docs as of mid-2026 and cross-referenced against this repo's actual code.
>
> Pinned versions (from [`pnpm-workspace.yaml`](../../../../pnpm-workspace.yaml)): `drizzle-orm ^0.45.2`, `drizzle-kit ^0.31.10`, `better-auth ^1.6.23`, `@better-auth/drizzle-adapter ^1.6.23`. Driver: `postgres` (postgres-js), **not** `pg`.

---

## 1. TL;DR

Drizzle is a TypeScript-first ORM where **your `.ts` schema files are the source of truth**. You declare tables with `pgTable(...)`, and `drizzle-kit` diffs those declarations against a stored snapshot to generate SQL migrations. There is no separate DSL — everything is TypeScript, so anything you can do in TS (spread helpers, shared column bags, `$type<T>()`) you can do in a schema. In this repo the schema lives under `packages/database/src/schema/`, is exported through `src/schema/index.ts`, and `drizzle.config.ts` points `schema` at that barrel file so the CLI picks up every table recursively.

The single most important repo-specific rule: **`src/schema/auth.ts` is machine-generated by the better-auth CLI (`pnpm auth:generate`) and must never be hand-edited.** The CLI rewrites the whole file on every run, including the `relations()` blocks that are aligned to better-auth's `experimental.joins: true`. To add fields to a user, you create a **1-to-1 satellite table** in a new file (`profile`, `settings`, …) rather than touching the four owned tables (`user`, `session`, `account`, `verification`). This is enforced in [`packages/database/AGENTS.md`](../../../../packages/database/AGENTS.md).

On the relations front there are two APIs. **v1 `relations()`** (per-table objects passed to `drizzle({ schema })`) is what we ship today and what the better-auth CLI emits. **v2 `defineRelations(schema, (r) => …)`** is the future — one central relations object, `from`/`to` instead of `fields`/`references`, `alias` instead of `relationName`, native many-to-many via `through`, and object-style `where`/`orderBy` in the query builder. As of mid-2026 v2 ships only on the `@rc` channel as part of the drizzle-orm/drizzle-kit **v1.0 beta line** — do not migrate the database package to it while we are pinned to `0.45.x`.

For connections we use postgres-js with serverless-safe settings (`prepare: false`, `max: 10`, `idle_timeout: 60`, `max_lifetime: 1800`) documented inline in [`src/client.ts`](../../../../packages/database/src/client.ts). `prepare: false` is mandatory behind a transaction-mode pooler (PgBouncer / Neon pooler); the extended-query protocol used by prepared statements is incompatible with it.

## 2. Schema organization layouts

Drizzle explicitly supports several layouts — the docs say "whichever you prefer, all the freedom." The `schema` key in `drizzle.config.ts` can point at a single file **or** a folder (walked recursively); the only hard requirement is that every table/enum/sequence is **exported** so the kit can import it for the diff.

| Layout | Shape | Best when | Trade-offs |
|---|---|---|---|
| **Single file** (`schema.ts`) | All tables in one file | Small schemas, prototypes | Merge conflicts and scroll fatigue as it grows |
| **Multi-file, one table per file** (`schema/users.ts`, `schema/posts.ts`) | Folder of files, `config.schema` points at the folder | Medium/large schemas, clear ownership | Cross-file FK references need explicit imports |
| **Per-feature / domain grouping** (`schema/auth.ts`, `schema/billing.ts`) | Files grouped by domain, re-exported via a barrel | Feature teams, satellite-table pattern | Slight ambiguity on where a shared table belongs |
| **Colocated with queries** (`feature/*.sql.ts` next to `feature/queries.ts`) | Schema files live inside feature folders | Vertical-slice / modular monolith | Config `schema` glob must reach all of them |

**This repo uses per-feature grouping with a barrel.** `drizzle.config.ts` sets `schema: "./src/schema/index.ts"`, and [`src/schema/index.ts`](../../../../packages/database/src/schema/index.ts) does `export * from "./auth"`. New tables go in `src/schema/<feature>.ts` and get re-exported from that barrel. There is also an empty `src/tables/index.ts` placeholder — schema, not tables, is the live path.

**Recommendation criteria.** Fewer than ~8 tables → single file is fine. More than that, or multiple contributors → split by feature. Because our auth tables are regenerated wholesale, isolating them in `auth.ts` and keeping everything else in sibling files is not optional here — it is the mechanism that keeps `pnpm auth:generate` from clobbering domain code.

**Shared column bags.** A common Drizzle idiom (from the official Schema doc) is to factor `created_at` / `updated_at` / `deleted_at` into a `timestamps` object and spread it into every table:

```ts
// columns.helpers.ts
export const timestamps = {
  updatedAt: timestamp("updated_at").defaultNow().$onUpdate(() => new Date()).notNull(),
  createdAt: timestamp("created_at").defaultNow().notNull(),
  deletedAt: timestamp("deleted_at"), // nullable → soft delete
}
// posts.ts
export const posts = pgTable("posts", { id: text("id").primaryKey(), ...timestamps })
```

## 3. Table and column patterns

### 3.1 `pgTable` basics

A table is `pgTable(dbName, columns, (table) => [ …constraints… ])`. The third argument returns an **array** of indexes/constraints in current Drizzle (older docs used an object — array is the modern form). Column TS keys map to DB names by default; pass an explicit name string to alias (`text("email_address")`). You can also let Drizzle auto-map camelCase→snake_case with the `snakeCase.table` / `camelCase.table` builders, but this repo writes the DB names explicitly.

### 3.2 Column types, defaults, nullability

- **`notNull()`** adds `NOT NULL`. Columns are nullable by default; a nullable column infers as `T | null`.
- **`.default(value)`** is a *SQL-level* default baked into the migration. **`.$default(fn)` / `.$defaultFn(fn)`** run in JS at insert time (e.g. `createId()`) and **do not** affect drizzle-kit output — runtime only.
- **`.$onUpdate(fn)` / `.$onUpdateFn(fn)`** run in JS on every update (and on insert if no other default is set). Also runtime-only; not reflected in migrations.
- **`.unique()`** / **`.primaryKey()`** are column-level constraints.

Concrete example straight from this repo's generated [`auth.ts`](../../../../packages/database/src/schema/auth.ts) `user` table:

```ts
export const user = pgTable("user", {
  id: text("id").primaryKey(),
  name: text("name").notNull(),
  email: text("email").notNull().unique(),
  emailVerified: boolean("email_verified").default(false).notNull(),
  image: text("image"),                                    // nullable
  createdAt: timestamp("created_at").defaultNow().notNull(),
  updatedAt: timestamp("updated_at")
    .defaultNow()
    .$onUpdate(() => /* @__PURE__ */ new Date())           // JS-side touch on update
    .notNull(),
});
```

### 3.3 Timestamps and `withTimezone`

- **`defaultNow()`** emits `DEFAULT now()`.
- **`timestamp("col", { withTimezone: true })`** produces `timestamptz`. Prefer this for anything user-facing to avoid ambiguity; the better-auth-generated columns here use plain `timestamp` (no tz), which is a known better-auth output detail, not a choice we can change without breaking regeneration.
- **`mode: 'date'`** (default) maps to a JS `Date`; **`mode: 'string'`** keeps the raw string. `precision: 3` controls fractional seconds.

### 3.4 Soft delete

Drizzle has no built-in soft delete — the community pattern (Discussion #4031, and multiple write-ups) is a **nullable `deletedAt` timestamp** plus a query-side filter:

```ts
deletedAt: timestamp("deleted_at", { withTimezone: true }), // null = live row

// "delete" = update
await db.update(posts).set({ deletedAt: new Date() }).where(eq(posts.id, id));

// read only live rows
await db.select().from(posts).where(isNull(posts.deletedAt));
```

Wrap the `isNull(deletedAt)` filter in a helper (or a view) so you cannot forget it. A **partial index** `where(sql\`deleted_at is null\`)` keeps lookups on live rows fast (see §8).

### 3.5 JSON columns

Use `jsonb` on Postgres (better than `json` — binary, indexable). Attach a TS shape with **`$type<T>()`**:

```ts
import { jsonb } from "drizzle-orm/pg-core";
metadata: jsonb("metadata").$type<{ theme: "light" | "dark"; flags: string[] }>().default({ theme: "light", flags: [] }).notNull(),
```

Notes: `$type<T>()` is a compile-time cast only — it does **not** validate at runtime, so pair it with Zod on the write path. Index JSON with an expression/GIN index; query with `->>` via `sql\`\``. The better-auth CLI emits `jsonb` for JSON fields on the `pg` provider.

### 3.6 Type inference

Prefer the per-table static properties:

```ts
type User       = typeof user.$inferSelect;   // shape returned by SELECT
type NewUser    = typeof user.$inferInsert;    // shape accepted by INSERT (optionals where defaults exist)
```

The older `InferSelectModel<typeof user>` / `InferInsertModel<typeof user>` from `drizzle-orm` are equivalent and still exported. For projections/deriving column subsets, `getColumns(table)` (a "goodie") lets you strip columns before a select. Known sharp edge: `$inferInsert`/`$inferSelect` are not freely composable (drizzle-orm #3528) — build your own helper types on top rather than nesting them.

## 4. Relations API — v1 vs v2

Relations are the metadata that powers the relational query builder (`db.query.user.findMany({ with: { sessions: true } })`). They are **not** DB constraints — FK constraints are declared separately with `.references()` / `foreignKey()`.

| Aspect | v1 `relations()` (shipped here) | v2 `defineRelations()` (RC) |
|---|---|---|
| Import | `import { relations } from "drizzle-orm"` | `import { defineRelations } from "drizzle-orm"` |
| Declaration | One `relations(table, …)` object per table | One central object keyed by table name |
| Passed to db | `drizzle(url, { schema })` | `drizzle(url, { relations })` |
| Field mapping | `fields:` / `references:` | `from:` / `to:` (each accepts single value or array) |
| Disambiguation | `relationName: "author_post"` | `alias: "author_post"` |
| Many-to-many | Manual junction table + nested query mapping | Native `r.many.groups({ from: r.users.id.through(r.usersToGroups.userId), to: … })` |
| `many` without `one` | Required declaring both sides | `many` side stand-alone |
| Query `where`/`orderBy` | Callback form `(t, { eq }) => …` | Object form `{ where: { id: 1 }, orderBy: { id: "asc" } }`, plus `AND`/`OR`/`NOT`/`RAW`, filter-by-relation, offset on related rows |
| Split across files | N/A | `defineRelationsPart(...)` then spread into `{ relations: { ...a, ...b } }` |

**What we ship today (v1).** [`auth.ts`](../../../../packages/database/src/schema/auth.ts) declares `userRelations`, `sessionRelations`, `accountRelations` with the classic `relations(user, ({ many }) => ({ sessions: many(session) }))` form, and [`packages/auth/src/auth.ts`](../../../../packages/auth/src/auth.ts) passes `schema` (not `relations`) into `drizzleAdapter(db, { provider: "pg", schema })`. The `relationName` on these blocks is generated by the CLI to match `experimental.joins: true` — per `AGENTS.md`, hand-editing them breaks that alignment.

**Migration notes (do NOT do this in the DB package yet).** v2 requires the whole ecosystem to move to the RC line, and the better-auth CLI must emit v2 syntax before we could regenerate `auth.ts` in v2 form. The official v1→v2 path: `drizzle-kit pull` can emit a `drizzle/relations.ts` in the new syntax; you copy it into your source relations file, fix the `import * as schema` path, and swap `drizzle(url, { schema })` → `drizzle(url, { relations })`. Also note the internal cleanup — v2 **removes** many exports (`Relations`, `relations` from the old path, `createTableRelationsHelpers`, etc.), so a mixed-version codebase produces import-not-found noise. Treat v1→v2 as a coordinated, whole-repo change, tracked against the version watch in §8.

## 5. Migrations workflow

`drizzle-kit` commands are wired into [`packages/database/package.json`](../../../../packages/database/package.json) as `db:generate`, `db:migrate`, `db:push`, `db:studio`, `db:check`.

| Command | What it does | When |
|---|---|---|
| `generate` | Diffs schema vs the stored snapshot, writes a numbered `NNNN_name.sql` + a matching `meta/NNNN_snapshot.json` + a `_journal.json` entry | Committing a schema change |
| `migrate` | Applies pending SQL files against the DB, records them | Staging / prod |
| `push` | Diffs schema directly against the live DB and applies it, **no SQL file** | Local dev iteration only |
| `pull` | Introspects an existing DB into schema (and, on RC, a v2 `relations.ts`) | Adopting an existing DB |
| `studio` | Local GUI browser for the DB | Ad-hoc inspection |
| `check` | Validates the migration folder for collisions / broken parent-snapshot chains | CI, before merge |

**Naming.** Auto-generated tags are `NNNN_<random-words>` (e.g. this repo's `0000_boring_steel_serpent` in [`drizzle/meta/_journal.json`](../../../../packages/database/drizzle/meta/_journal.json)). `--name` sets a human tag; `--custom` scaffolds an empty SQL file for hand-written data migrations/seeds.

**The v7 snapshot format.** Each migration has a companion `meta/NNNN_snapshot.json`. Ours is `"version": "7"` with `"dialect": "postgresql"`, an `id`/`prevId` chain, and a `tables` map (each table records columns, `notNull`, `primaryKey`, indexes, FKs). The `_journal.json` is `"version": "7"` and lists entries by `idx`, `tag`, and `when` (epoch ms). Snapshots are the diff base — **the schema files, plus the latest snapshot, together determine the next migration.** Never edit a committed snapshot by hand.

**Dev vs prod flow in this repo:** `pnpm db:generate` to author the migration → `pnpm db:push` locally → `pnpm db:migrate` in staging/prod (per `AGENTS.md`). Tests apply the *existing* migrations via `drizzle-orm/postgres-js/migrator` rather than duplicating table SQL.

**The #5774 gotcha (matches our exact pins).** `drizzle-kit generate` computes the next index from the **journal alone** — `idx = lastEntryInJournal.idx + 1` — without cross-checking on-disk `drizzle/*.sql`. If the journal is stale versus the on-disk files (partial rebase, cherry-picked migration files, manual journal repair), `generate` writes a **colliding prefix** and **silently overwrites** the existing `meta/NNNN_snapshot.json` with no existence check. It is silent at author time; you catch it with `git diff drizzle/meta/`. Filed 2026-05-17 against `drizzle-orm ^0.45.2` / `drizzle-kit ^0.31.10` (our versions), still **open** as of mid-2026. Mitigation: run `pnpm db:check` in CI, review `git diff` on `drizzle/meta/` before committing, and never merge two branches that each added a migration without regenerating.

## 6. Better-auth CLI integration

**Command.** `pnpm auth:generate` (root) → `pnpm --filter @workspace/auth auth:generate` → `pnpm exec auth generate --config ./src/auth.ts --output ../database/src/schema/auth.ts --yes` (see [`packages/auth/package.json`](../../../../packages/auth/package.json)). It reads the better-auth config in [`packages/auth/src/auth.ts`](../../../../packages/auth/src/auth.ts) (plugins, `emailAndPassword`, `experimental.joins`, etc.) and emits the Drizzle schema.

**What it overwrites.** The whole `src/schema/auth.ts` file, every run — tables `user`, `session`, `account`, `verification`, their indexes, and the `relations()` blocks. Any manual edit is silently lost. This is why those four tables are declared "owned by better-auth" and off-limits.

**Satellite table pattern.** To extend user data, do **not** add columns to `auth.ts`. Create a 1-to-1 table in `src/schema/<feature>.ts` keyed on `user.id` with `onDelete: "cascade"`, add its own `relations()`, re-export from `src/schema/index.ts`, then `pnpm db:generate`:

```ts
// src/schema/profile.ts
export const profile = pgTable("profile", {
  userId: text("user_id").primaryKey().references(() => user.id, { onDelete: "cascade" }),
  // custom fields here
})
export const profileRelations = relations(profile, ({ one }) => ({
  user: one(user, { fields: [profile.userId], references: [user.id] }),
}))
```

A satellite survives regeneration, isolates the domain, and avoids merge conflicts against the generated file.

**`usePlural`.** If all your app tables are plural, pass `usePlural: true` to `drizzleAdapter` and the CLI generates `users`, `sessions`, … instead of the singular names. **This repo uses singular** (`user`, `session`, …) — do not flip `usePlural` unless you regenerate and migrate everything, and note the open better-auth bug #3069 where `usePlural` misbehaves with custom schema names. The CLI also honors field-name overrides via the Drizzle column alias or the auth config's `fields` / `modelName` maps. **`relationName`**: the CLI emits it on relations to keep `experimental.joins: true` (enabled in our `auth.ts`) working — leave it alone.

Note: `provider: "pg"` in the adapter selects Postgres output (`jsonb`, `timestamp`, `text` ids). The CLI groups imports as `drizzle-orm` (root, e.g. `sql`) + `drizzle-orm/pg-core` (column builders).

## 7. Pitfalls & gotchas

- **Hand-editing `src/schema/auth.ts`** → silently overwritten by the next `pnpm auth:generate`. Extend via satellite tables instead.
- **drizzle-orm #5774** → `generate` overwrites a snapshot / collides prefixes when the journal is stale. Run `db:check` in CI and diff `drizzle/meta/` before commit.
- **Breaking `relationName` alignment** in `auth.ts` → breaks better-auth `experimental.joins`. Regenerate, don't edit.
- **Relations v1→v2 migration noise** → v2 removes ~16 old exports; a half-migrated tree throws import errors. Migrate the whole package at once, only on the RC line.
- **Flipping `usePlural`** without regenerating + migrating → schema/DB drift; plus better-auth #3069 with custom schema names.
- **`$default` / `$onUpdate` don't touch migrations** → they are runtime-only. A JS default will not appear as a SQL `DEFAULT`; add `.default(...)` if you need it in the DB.
- **`$type<T>()` gives no runtime validation** → validate JSON with Zod on writes.
- **`prepare: true` behind a transaction-mode pooler** → prepared statements break; keep `prepare: false` (see §12).
- **Missing `notNull()`** silently makes a column nullable and infers `T | null`; be deliberate.
- **`push` in prod** → no SQL artifact, no review trail. `push` is dev-only; use `generate` + `migrate` for staging/prod.
- **Two branches each adding a migration** → merge produces duplicate `idx`/prefix and parent-snapshot collisions (#3935-class); `db:check` catches these.
- **Editing a committed snapshot** → corrupts the diff base; regenerate instead.

## 9. Connection management (postgres-js)

We connect with **postgres-js** (`drizzle-orm/postgres-js` + `postgres`), not `pg`. [`src/client.ts`](../../../../packages/database/src/client.ts) creates the pool lazily behind a `Proxy` so imports don't crash when `DATABASE_URL` is unset (the `pnpm auth:generate` CLI context returns a passthrough stub). The tuned options, documented inline:

```ts
const pool = postgres(url, {
  prepare: false,        // required behind PgBouncer / Neon pooler (transaction mode)
  max: 10,               // cap connections per Lambda/worker; tune to provider limits
  idle_timeout: 60,      // close idle conns after 60s (Neon compute suspends ~5min)
  max_lifetime: 60 * 30, // recycle every 30min to stay fresh
})
const db = drizzle(pool, { schema })
```

- **`prepare: false`** is the load-bearing one for serverless. Transaction-mode poolers (PgBouncer, Neon pooler, Supabase pooler) hand a different backend connection per transaction, which is incompatible with Postgres' extended-query/prepared-statement protocol. Leaving `prepare: true` behind such a pooler causes `prepared statement "s1" already exists` / protocol errors. This is called out in the Drizzle Supabase connect docs and the porsager/postgres pooling discussion.
- **`max`** should be small per instance in serverless — many concurrent Lambdas each holding a pool will otherwise exhaust the DB's connection limit. 10 is a conservative cap; lower it if you run high fan-out.
- **`idle_timeout`** was raised from an earlier aggressive 20s because Neon's pooler was resetting connections (`ECONNRESET`); 60s is the documented value.
- **`max_lifetime`** recycles connections periodically so you don't hold a stale backend across a pooler restart.

Per [`packages/database/AGENTS.md`](../../../../packages/database/AGENTS.md), do not change these values without a documented reason. Tests default to **pg-mem** (no real Postgres); `TEST_DATABASE_URL=… pnpm test` switches to a real connection.
