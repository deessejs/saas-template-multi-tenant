## TL;DR

After this PR merges, every email+password signup automatically provisions a personal organization (via `databaseHooks.session.create.before`), `auth.api.*` and `authClient.organization.*` are usable from `apps/app`, the auth schema includes the `organization`, `member`, and `invitation` tables, and React components can rely on `useActiveOrganization()` without the upstream `#9710` stale-state bug biting.

```ts
// Mirrors docs/guides/better-auth/org.md § Slug helper.
// 40-char cap, URL-safe, kebab-case.
const slugify = (text: string): string =>
  text
    .toLowerCase()
    .trim()
    .replace(/[^\w\s-]/g, "")
    .replace(/[\s_-]+/g, "-")
    .replace(/^-+|-+$/g, "")
    .slice(0, 40)
```

Per feedback memory `[[feedback-long-term-solutions]]`, keep it in `auth.ts` until a second consumer exists. Do NOT split into `slugify.ts`.

### Step 2 — Add `databaseHooks.session.create.before` for auto-create on signup

Same file `auth.ts`.

- Add a `databaseHooks` key on the `betterAuth({...})` call with a `session.create.before` hook.
- The hook fires on every new session. To distinguish first-signup auto-create from subsequent signins: read the user's current orgs via `auth.api.listOrganizations(...)`. If they already have an org, return `session` unchanged. Otherwise create the personal org.
- Follow `docs/guides/better-auth/hooks.md` § Session.create.before — Key Use Case.

#### 2.1 — Resolve user display name

Inside the hook:

```ts
databaseHooks: {
  session: {
    create: {
      before: async (session, _ctx) => {
        const s = session as typeof session & {
          user?: { name?: string; email?: string; id?: string }
        }
        const displayName =
          s.user?.name ??
          s.user?.email?.split("@")[0] ??
          "Personal"

        // ...create org, see 2.2...
      },
    },
  },
},
```

The fallback chain `name → email local part → "Personal"` matches `hooks.md`.

#### 2.2 — Call `auth.api.createOrganization` server-side

```ts
const org = await (auth.api as any).createOrganization({
  body: {
    name: `${displayName}'s workspace`,
    slug: slugify(displayName),
  },
  headers: new Headers(),
})

if (!org?.id) {
  // Org creation can fail with ORGANIZATION_SLUG_ALREADY_TAKEN on collision.
  // Fall back to a unique slug so the signup completes regardless.
  const fallbackSlug = `${slugify(displayName)}-${Math.random().toString(36).slice(2, 8)}`
  const retried = await (auth.api as any).createOrganization({
    body: { name: `${displayName}'s workspace`, slug: fallbackSlug },
    headers: new Headers(),
  })
  return {
    data: { ...session, activeOrganizationId: retried.id },
  }
}

return { data: { ...session, activeOrganizationId: org.id } }
```

The `(auth.api as any)` cast is required because better-auth's TS types don't include plugin-augmented methods until a typed wrapper is generated. See Risks.

A fallback to a random slug handles duplicate display names (two users both named "Alice") without crashing the signup. The 6-char random suffix is sufficient entropy for the user-table cardinality this template targets.

#### 2.3 — Return session with `activeOrganizationId`

```ts
return { data: { ...session, activeOrganizationId: org.id } }
```

Merging the column into the session object before insert. better-auth writes it to the new `session` row.

#### 3.3 — Add Drizzle relations for the new tables

The CLI emits basic relations for `user` ↔ `session` and `user` ↔ `account`. Add the missing relations for the new tables (required by `experimental.joins: true`, already enabled in `auth.ts:64`):

```ts
// Append to packages/database/src/schema/auth.ts after regen
export const memberRelations = relations(member, ({ one }) => ({
  user: one(user, { fields: [member.userId], references: [user.id], relationName: "user_member" }),
  organization: one(organization, { fields: [member.organizationId], references: [organization.id] }),
}))

export const invitationRelations = relations(invitation, ({ one }) => ({
  organization: one(organization, { fields: [invitation.organizationId], references: [organization.id] }),
  inviter: one(user, { fields: [invitation.inviterId], references: [user.id], relationName: "user_invitation" }),
}))

export const organizationRelations = relations(organization, ({ many }) => ({
  members: many(member),
  invitations: many(invitation),
}))
```

`relationName` is required when multiple FKs point from one table to another (`user` is referenced from `session`, `account`, `member`, `invitation`). Mirror whatever the CLI emits for `sessionRelations` / `accountRelations` for consistency — same pattern.

### Step 4 — Update `auth-client.ts` with the `#9710` workaround

`apps/app/lib/auth-client.ts`

The file currently has only:

```ts
export const authClient: ReturnType<typeof createAuthClient> = createAuthClient({
  baseURL: clientEnv.NEXT_PUBLIC_APP_URL,
})
```

Apply the upstream workaround to invalidate `$activeOrgSignal` on every `$sessionSignal` change (per `docs/guides/better-auth/client.md` § useActiveOrganization — Stale Cache Bug):

```ts
import { createAuthClient } from "better-auth/react"
import { organizationClient } from "better-auth/client/plugins"
import { clientEnv } from "@workspace/env/client"

export const authClient = createAuthClient({
  baseURL: clientEnv.NEXT_PUBLIC_APP_URL,
  plugins: [organizationClient()],
})

// Workaround for better-auth #9710:
// $activeOrgSignal does not invalidate on /sign-in/email, so useActiveOrganization
// returns stale null after sign-in. Forward $sessionSignal changes to invalidate.
let initialized = false
authClient.$sessionSignal.subscribe(() => {
  if (initialized) {
    authClient.$activeOrgSignal.value = null
  }
  initialized = true
})
```

Add `organizationClient()` to the plugins so React hooks (`useActiveOrganization`, `useActiveMemberRole`) are generated. Without it, the workaround has nothing to invalidate.

The TS-arrow-style from feedback memory `[[feedback-ts-arrow-style]]` doesn't apply here — the existing file is already arrow-style and we're only modifying the `authClient` config and adding a side-effecting subscription.

## Risks / edge cases

- **CLI 1.4.21 vs runtime 1.6.23 skew** — per memory `[[better-auth-cli-release-blocker]]`. `pnpm auth:generate` may not emit all required columns or relations, or may error out entirely. If it errors, this PR cannot land until the CLI is bumped (track as a separate PR). If it omits columns, apply them manually per AGENTS.md and document in the PR description.

- **Open bug better-auth `#9070`** — `session.create.before` is documented as unable to query membership rows on the first signup because the org plugin creates membership AFTER the session insert. Our implementation sidesteps this by creating the org INSIDE the hook (not after), which is not documented as supported but has not been observed to fail. **Test plan when landing this PR**:
  1. Sign up a brand new user
  2. Verify `activeOrganizationId` is set in the `session` DB row
  3. Verify `useActiveOrganization()` (with the `#9710` workaround applied) returns the org on the client
  4. Sign out + sign back in — confirm it still works
  If step 3 fails, the workaround is broken — defer the workaround application to a follow-up and document.

- **Open bug better-auth `#9710`** — `useActiveOrganization` returns stale null after sign-in because `$activeOrgSignal` does not invalidate on the `/sign-in/email` path. Our workaround in Step 4 mitigates this client-side. Upstream fix PRs `#9736` / `#9737` are pending; when merged, the workaround becomes obsolete. Track a rebase.

- **`(auth.api as any)` cast** in the auto-create hook — needed because better-auth's runtime `auth.api` is augmented by the plugin but the TS types are not. The cast is brittle. Track a follow-up to either (a) upgrade better-auth types or (b) add a local typed wrapper in `packages/auth/src/api-types.ts`.

- **Slug collisions** between two users with the same display name. Better-auth throws `ORGANIZATION_SLUG_ALREADY_TAKEN` on `createOrganization`. Step 2.2 retries with a 6-char random suffix. **Risk:** if a user signs up from a region with sparse randomness, two collisions in a row are statistically improbable but possible. Acceptable for this template; for a production template, switch to a server-issued nonce in the org creation endpoint.

- **`authClient.$activeOrgSignal`** — accesses a possibly undocumented internal. Better-auth 1.6.x exposes this as a `$state` atom on the client. If it changes name in 1.7+, the workaround in Step 4 will silently no-op. There is no public API replacement yet — track upstream.

- **Slug helper is inlined in `auth.ts`** — if a second consumer emerges (e.g., a future `customSlug` for teams), the helper should split into `packages/auth/src/slugify.ts`. Until then, inlining is the project preference per `[[feedback-long-term-solutions]]`.

- **The 4-gate proxy chain described in `docs/internal/specs/organizations/onboarding/README.md`** is a *spec*, not a constraint of this PR. The current proxy.ts has only 3 gates (no onboarding gate). The auto-create on signup works WITHOUT the onboarding page — users land on `/home` with an active org set, which is fine for now. A separate follow-up should land the gates (and the new `/onboarding/first-organization` / `/accept-invitation` pages), but neither blocks this PR.

- **Header UI update deferred** — `#12` AC mentions `apps/app/components/header` reflecting `useActiveOrganization`. We interpret this as wiring the workaround in `auth-client.ts` (Step 4). The header UI itself does not consume `useActiveOrganization` yet — that ships with the future OrgSwitcher issue. If the reviewer interprets the AC strictly, this PR is incomplete; if generously, it's complete.

- **Index markdown update is a one-line flip** — moving `Locked` → `Implemented`. If the upstream later changes APIs (e.g., `autoCreateOrganizationOnSignUp` becomes supported differently, or `#9070` is fixed), the index becomes out of date. Track as a rebase concern.
